# skill.md — deck49 (Dragons) wave-19 contributions (REVISED-GUIDE ROUND-2 RE-VALIDATION)

deck49's second guided corpus is the clean worked example of a wave-18 method promise coming due: a
SUPPRESSION was replaced by an ANNOTATION, the masked class re-appeared, and the guide rule that
pairs with it was finally TESTED. Proposed additions/confirmations (single-seat unless noted):

## CONFIRMED rungs (existing doctrine, re-proven at round 2)

- **(the mask-lift re-test discharged) a class recorded "masked, re-test when the mask lifts" MUST be
  re-tested on the corpus where the mask lifts — and the verdict is only valid then.** Wave-18 filed
  C4 (never-aura enemy-only) as "masked, not proven-solved" because E-49c suppression hid every
  enemy-only War Paint. Wave-19 shipped the suppression->annotation swap; enemy-only War Paint
  reappeared (deck135 s4/s5/s7 with the "every legal target is the OPPONENT's" warning); the model
  declined 3/3 with the buff-helps-them logic, 0 loops. Only NOW is C4 "solved." This closes the
  wave-18 WATCH exactly as scheduled — the mask-lift ledger discipline works end to end.

- **(rule 1 re-proven) read the tax collapse, not the record — twice.** deck49 went 2/6->5/6 this
  wave while every taught class stayed dead/held and fallbacks stayed at 0. The record moved on the
  pool (flipped vs14/vs62/vs35 from L to W; deck21/17 out, deck27 in). Two consecutive corpora now
  show the guide's JOB met independent of a swinging record.

- **(representation-beats-instruction, refined) an ANNOTATION carries only the case it renders; the
  GUIDE rule still owns the cases the annotation does not cover.** The E-49c annotation fires only on
  the ENEMY-ONLY menu. The MIXED menu (own + opponent targets, deck62 s10/s11) gets NO warning — and
  there the model still correctly chose its own Bloodmark Mentor over the opponent's Birds/Saprolings,
  driven by the guide's never-aura rule. LESSON: before trimming a strategic rule as "now redundant
  with the engine annotation," check the annotation's SCOPE. If the annotation is conditional (only
  the enemy-only case), the rule remains load-bearing for the complementary case and is NOT a trim
  candidate. This is the boundary condition on wave-18's concurrent-engine-fix apportionment: apportion
  by the annotation's ACTUAL trigger surface, not by the class name.

## CONFIRMED instrument (adopted wave-18, re-run)

- **The burn-target-menu face-rate, scored against offered enemy creatures — with the sanctioned
  exception counted as a PASS.** deck49 scored 16/16 correct this wave: 15 face + 1 creature-target
  that was the guide's own exception (kill the flying defender+wither wall that would eat a Dragon,
  then second burn to face, deck27 s14). Refinement: the instrument must classify a creature-target
  as CORRECT when it matches the "real threat / key blocker walling the board" exception, not score it
  as a miss. The clean version is "(face + sanctioned-exception) / total burn menus," with the
  exception reads spot-checked for the wall/lethal-threat justification.

## NEW rung (proposed) — a trade-outcome ANNOTATION cross-checks a stale card-script value

**When the engine renders a per-pairing outcome annotation on a decision, it can OVERRIDE a stale
card-script stat the guide inherited — and the model trusts the rendered outcome.** deck14 s23: the
engine's Ashenmoor Liege is a 4/1 (card-script divergence — real/ guide say 4/4), so the block option
carried "(both die)"; the model read the annotation and blocked accordingly, never invoking the guide's
"4/4 anthem body" text. This is a second face of the two-sided trust rule (wave-18 headline 3): the
rendered OUTCOME annotation is a stronger, more local signal than a derived stat, and it silently
protects against guide/card-script stat drift. Method note for reviewers: a correct decision under an
outcome annotation is NOT evidence the underlying card-script stat is right — verify the stat
separately (Oracle queue), because the annotation is masking the divergence at decision time.

## WATCH carried forward (do not generalize yet)

- **An off-case authored proactively can go a whole corpus UNEXERCISED — that is expected, not a
  failure, but it defers the off-case's own validation.** deck49's flood/no-curve off-case (added
  wave-18) never fired this wave because the winning corpus never floods. Per Step-0-ter rule 6 we
  author it anyway, but its validation is still PENDING — it needs a flood game to confirm the mild
  burn-hold dies under it. Doctrine: track an unexercised off-case as an OPEN validation thread, not
  a closed one, and do not let its absence read as "the class is dead."
