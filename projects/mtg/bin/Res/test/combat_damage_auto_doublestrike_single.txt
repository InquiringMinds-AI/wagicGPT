# COMBAT DAMAGE AUTO-ASSIGNMENT pins (wave 44). The damage ASSIGNMENT window is
# auto-skipped by design - the owner's position is that the assignment has a
# deterministically correct answer, so automating it is reasonable rather than a
# bug. Because the player never sees that screen, GuiCombat::autoaffectDamage IS
# the assignment, so these fixtures pin what it computes. Note the SAME function
# is the AI's assignment too (AIPlayerBaka::affectCombatDamages calls it), so
# there is one definition for both seats.
#
# DOUBLE STRIKE + TRAMPLE, one blocker that SURVIVES the first-strike sub-step.
# Boros Swiftblade (1/2 double strike) + Rancor = 3/2 double strike trample vs
# Stone Golem 4/4. First strike assigns 3 to the Golem (lethal there is its full
# 4, so all 3 go in and nothing tramples), leaving it 1 remaining toughness. At
# the regular damage sub-step CR 702.19b requires lethal to "take into account
# damage already marked on the creature", so lethal is now 1, not the printed 4:
# autoaffectDamage assigns the Golem 1 and tramples the other 2 through.
# Defender ends on 18.
#
# This is the MAXIMAL line and the rules-correct one. Both are true at once -
# CR 510.1c also permits assigning MORE than lethal, so the old behavior here
# (3 again at the regular step, 0 trampled, defender on 20) was legal but left
# 2 damage on the table every time. autoaffectDamage now computes lethal from
# card->life, the same remaining-toughness value hasLethalDamage() and
# GuiCombat::removeOne already use. A regression back to card->toughness would
# make this number 20.
[INIT]
FIRSTMAIN
[PLAYER1]
inplay:Boros Swiftblade
hand:Rancor
manapool:{G}
life:20
[PLAYER2]
inplay:Stone Golem
life:20
[DO]
Rancor
Boros Swiftblade
goto attackers
Boros Swiftblade
next
Stone Golem
goto end
[ASSERT]
ENDOFTURN
[PLAYER1]
hand:Rancor
graveyard:Boros Swiftblade
life:20
[PLAYER2]
graveyard:Stone Golem
life:18
[END]
